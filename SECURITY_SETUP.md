# Security setup and release checks

The application keeps JSON documents in the existing private Vercel Blob store. No database or new service is required. This work does not deploy anything or update Vercel settings. Missing security/storage settings deny protected operations.

## Required configuration

Set these yourself in the appropriate Vercel environment. Never use a `NEXT_PUBLIC_` prefix for credentials. Do not paste credentials into an issue, chat, screenshot, report or committed file.

| Variable | Purpose |
| --- | --- |
| `BLOB_READ_WRITE_TOKEN` | Existing **private** Blob store. Required for production and Vercel previews that need mutable features. Its value must remain server-only. Filesystem mode is available only outside Vercel and outside production. |
| `ADMIN_PASSWORD_HASH` | Fresh versioned scrypt hash generated by the setup command below. Used only to bootstrap an absent `security/admin.json`. Once that document exists, this variable cannot override a changed password. Never reuse the tracked legacy hash. |
| `SECURITY_SECRET` | Random 32-byte secret encoded as 64 hexadecimal characters, generated by setup. Used to pseudonymize IP/email/duplicate rate-limit identifiers. Rotating it must be controlled because it changes those identifiers. |
| `APP_ORIGIN` | Exact canonical HTTPS origin, for example `https://www.example.com`; no path, query or fragment. `NEXT_PUBLIC_SITE_URL` is a fallback, but explicitly configure `APP_ORIGIN`. Vercel's own `VERCEL_URL` is also accepted for the current deployment. Request Host/Forwarded values do not expand this list. |
| `NEXT_PUBLIC_SITE_URL` | Public canonical site URL for SEO. Contains no secret. |
| `EMAIL_USER`, `EMAIL_PASS` | SMTP account and exact app-password bytes. `SMTP_USER`/`SMTP_PASS` remain supported aliases. For Gmail, enter the actual app password without display-formatting spaces. |
| `SMTP_HOST`, `SMTP_PORT` | Approved SMTP submission host and port. Default: Gmail host, port 465. Supported ports: 465 (implicit TLS), 587 or 2525 (mandatory verified STARTTLS). |
| `SMTP_FROM_EMAIL` | Optional authenticated sender email if the SMTP username is not itself an email address. |
| `CONTACT_RECEIVER_EMAIL` | Business inbox. `ENQUIRY_TO_EMAIL` remains supported; the public business address is the fallback. |

`CONTACT_EMAIL_ENABLED=false` pauses outbound emails while accepted enquiries continue to be stored. The default is enabled. Google reviews can continue to use server-only `GOOGLE_MAPS_API_KEY` and `GOOGLE_PLACE_ID`; apply the provider's appropriate API restrictions and quotas. `NEXT_PUBLIC_SHOW_TODO` has no effect in a production build.

### Provision the initial credential locally

On Windows, setup uses PowerShell's native secure prompt and displays asterisks as you type. If an older setup process is stuck at a completely blank prompt, press Ctrl+C and rerun `npm run security:setup` with the updated script. The password passes to the hashing process through stdin, never command arguments or environment variables. Other platforms retain hidden input.

Run `npm run security:setup` yourself in an interactive terminal. The command prompts twice with hidden input, enforces 12–256 characters, and writes `.security/bootstrap.env` using exclusive creation. It does not print passwords, hashes or secrets. The generated directory is ignored by Git; it is not a public asset.

Privately transfer the two generated values into your Vercel settings, and into `.env.local` only if local development needs them. The application does not automatically load `.security/bootstrap.env`. Protect that file with your operating system's access controls; Windows does not enforce POSIX mode bits. The setup command refuses to overwrite it.

The old `ADMIN_PASSWORD` variable is no longer accepted. Existing admin cookies are invalidated. First successful login creates `security/admin.json` in private storage. Existing `data/auth.json` and `collections/auth.json` are not used or deleted. Password changes update the private document and revoke all existing sessions, then issue a fresh session for the current device.

The login screen's existing password-change modal now requires a verified session. It is not an unauthenticated recovery mechanism. Forgotten-password recovery is a controlled operator task: generate a new hash offline, back up the existing private authentication document, conditionally replace its hash and set `sessions` to an empty array in the intended environment. Merely changing the bootstrap environment variable does not reset an existing administrator. No recovery operation was performed by this implementation.

## Persistent state and limits

- Origin validation accepts the configured canonical origin and Vercel's individual deployment URL. In a Vercel production deployment, it also accepts the platform-provided `VERCEL_PROJECT_PRODUCTION_URL`, so the stable production alias works without trusting request Host/Forwarded headers. Previews do not implicitly accept the production alias. Keep `APP_ORIGIN` set explicitly for any additional canonical address.
- The token in the cookie is random, 256-bit opaque data. Only its SHA-256 hash and absolute expiration are stored. Every private request verifies it against storage; there is no cross-request in-memory authentication cache.
- Normal sessions last at most 24 hours; remembered sessions at most 30 days. At most 20 sessions are retained. Logout persistently revokes the current session before reporting success. Cookies are HttpOnly, SameSite=Lax and Secure in production, with the `__Host-` prefix and Path=/.
- Scrypt uses N=131072, r=8, p=1, a random salt and an asynchronous server derivation. Each in-flight derivation needs approximately 128 MiB. Keep an adequate Vercel function memory allocation; shared limits run before expensive password work.
- Login and password-change limits: 5 attempts per pseudonymized client per 15 minutes and 60 total per action per 15 minutes. Limits include successful attempts, making the budget predictable. Temporary aggregate limits can deny legitimate access during an attack; do not replace them with permanent account lockout.
- Contact limits: 5 submissions per client per 10 minutes, 50 total per hour, one identical enquiry per 5 minutes, and at most 3 acknowledgement emails per recipient per day. Acknowledgement suppression does not delete an accepted enquiry. Storage failure denies submission and retains the WhatsApp fallback.
- Admin mutations: 120 per session per 10 minutes and 500 total per hour. Private JSON collections have an 8 MiB write ceiling and record limits: 2,000 images, 1,000 blog entries, 1,000 slots, 5,000 enquiries. Existing records are never automatically evicted to enforce these limits.
- Shared limits use fixed-name JSON documents under `security/rate-*.json`, ETag compare-and-swap, expiration and bounded active entries. They do not depend on process-local Maps or Vercel local disk. Concurrent first creation is conditional. Storage failure/contention fails closed.
- Sessions, auth and limits add operations to the **existing** Blob store. Review the account's usage/cost limits; no new paid resource was provisioned. Edge firewall limits can reduce attack traffic and storage-operation costs, but are not the application's only protection. Do not purchase a plan or create a store without separate approval.
- On Vercel, the application uses the platform-overwritten `x-vercel-forwarded-for` header. Elsewhere it uses a shared local/unknown client bucket. Do not run behind a different production proxy without explicitly adapting and testing its trusted-IP boundary.

## Uploads and rendering

Uploads are capped at 4 MiB, with a bounded multipart envelope, to fit Vercel's function request limit. Previous slot constants advertised larger local uploads that could not pass through Vercel's normal function ingress. Larger video uploads need a separately designed signed direct-to-private-Blob/quarantine flow; none was silently added.

Images are decoded and re-encoded using patched Sharp with pixel/frame limits; SVG is rejected. Videos require matching MP4/QuickTime/WebM container structures, bounded lengths and allowed MIME types; they are not transcoded by a full codec sandbox. Public media uses fixed prefixes, safe names, nosniff and a restrictive direct-navigation CSP. Existing media files were not rewritten or deleted.

Script CSP uses per-request nonces and strict-dynamic; it does not allow unsafe-inline or unsafe-eval in production scripts. Inline styles remain allowed for the existing animations and translation UI. Public HTML is now rendered per request to keep nonces correct; review latency/hosting usage. Do not cache HTML while reusing or mismatching nonces. Existing image/media caching remains separate. Third-party translation and analytics do not run on admin pages, which have no translation controls.

## Data and historical exposure review

`data/auth.json` and `data/enquiries.json` were preserved unchanged while the request to stop tracking them awaits a decision. `.gitignore` prevents new untracked runtime files from being added, but cannot untrack an existing file. `security:scan` checks tracked and new non-ignored files, public assets and available browser bundles. It warns about the legacy tracked files and rejects staging changed private runtime records. Do not claim this removes data from Git history.

Two historical `.env.example` revisions contain SMTP password candidates. Values were not printed; neither matched the current local password during the audit. **Confirm with the mail account owner that those historical app passwords are revoked.** A different current app password does not prove the old ones were revoked. This is a release gate, especially for a public repository.

Review repository visibility, who can access the historical customer records, and whether redacted fixtures should replace them. No history rewrite, credential revocation, record deletion or private file removal was automated. Existing Blob content must be inventoried/backed up before any manual migration; local JSON records are not automatically imported into a new Blob store.

## Verification before release

Run:

```text
npm ci
npm run lint
npm run typecheck
npm run test:security
npm audit
npm audit --omit=dev
npm run build
npm run security:scan
npm run test:production
```

The production smoke command starts and stops a loopback-only server on port 3100, disables external credentials only in its child process, and sends no real emails or Blob writes. It does not change environment files or Vercel settings. The security tests use isolated fake I/O and temporary directories, including concurrent instances, and do not modify project data. Node 22+ is recommended for the test tooling.

On the intended protected Vercel preview, manually verify the private store's actual ETag semantics under parallel requests, known-session login/logout replay, password-change revocation, shared rate limits across function instances, HTTPS/cookie attributes, canonical and deployment origins, denied cross-origin requests, sanitized provider failures, and secret/private-JSON HTTP denial. Keep preview and production storage/credentials separate; a preview with no approved store must leave mutable features unavailable.

Verify custom-domain HTTPS redirects and deployed headers. Check mail delivery and SPF/DKIM/DMARC with your provider. Protect Vercel/Git accounts with MFA and least privilege; enable usage alerts and private backups. Public pages, French translation, the login screen and mobile overflow were checked locally in Chrome; a complete visual comparison of authenticated admin workflows and all devices still requires a configured preview.

The package lock contains a scoped local adapter replacing Next ESLint's vulnerable fast-glob dependency with the already-used tinyglobby library. It implements the plugin's only used API, including directory expansion/trailing-separator compatibility. A regression test exercises brace directory patterns. Revisit this workaround when upstream removes or patches the vulnerable dependency; do not remove it without rerunning the full audit and lint checks.

# Security implementation report

Updated: 23 October 2026. Original audit: 3 Critical, 3 High, 9 Medium, 3 Low findings.

The authentication bypasses, default passwords, session lifecycle defects, shared-limit gaps and application hardening findings have been addressed in code. The existing JSON architecture and public visual design were retained. **Production release is conditional on the manual gates below; S12 is not represented as fully resolved.** No deployment, push, history rewrite, production environment update or customer-data deletion was performed.

## Architecture after implementation

- Next.js App Router with TypeScript and React; patched Next.js 16.4.2 and Sharp 0.35.5. No database or new hosting service.
- Existing private Vercel Blob holds JSON collections and fixed-prefix security JSON documents. Production/Vercel runtimes refuse filesystem fallback. Development uses private `.security` state plus existing local data collections.
- Every protected page and all 16 operations in the eight admin API route files verify authorization server-side. The proxy also verifies sessions, but handlers and actions do not rely solely on it.
- Sessions use random 256-bit opaque cookies; only token hashes and absolute expirations are stored. Normal lifetime: 24 hours; remembered lifetime: 30 days. Logout revokes the active token persistently. Password change revokes previous sessions and creates a new current-device session. Password derivation is asynchronous, versioned scrypt with explicit strong parameters.
- Shared auth/contact/mutation/recipient limits use conditional writes to bounded, fixed-name private JSON documents, not local disk or instance memory. Origin checks run inside public/privileged actions regardless of the URL used to invoke them.
- Images are decoded/re-encoded; video containers and request sizes are bounded. Public media cannot select private document paths. Email HTML is escaped, SMTP transport is validated and encrypted, diagnostics/logs are minimized.
- Public HTML uses per-request CSP nonces; browser checks confirmed translation continues to work. Admin pages exclude third-party translation/analytics. No layout, style, animation or public contact link was redesigned.

## Required manual release gates

1. Configure the existing private Blob token, newly generated `ADMIN_PASSWORD_HASH`, `SECURITY_SECRET`, canonical `APP_ORIGIN`, and SMTP settings as described in the runbook. No default admin access is available. Do not send secret values through chat.
2. Resolve S12's Git-tracking decision without deleting data, review repository access/customer-record authenticity, and confirm old SMTP app passwords are revoked. No history rewrite or external credential change has been performed.
3. On an approved isolated Vercel preview, verify actual Blob conditional-write behavior, cross-instance throttling/revocation, successful authenticated admin workflows, provider failures and SMTP delivery. Unit concurrency tests do not prove a remote store's configuration or consistency.
4. Verify HTTPS redirects, cookie attributes and headers on the actual custom domain; confirm Vercel/Git MFA, deployment/preview access, usage alerts and private backups. No new paid infrastructure was provisioned. Existing Blob operation costs increase with server-side security checks; edge limits can reduce attack costs.

## Compatibility and operational changes

- Follow-up: login now enforces a server-only `ADMIN_EMAIL` together with the password (`src/lib/security/identity.ts:14`, `src/app/actions/admin-auth.ts:35`). Previously the form displayed an email field but the action ignored it; a password was still required. Email normalization is bounded, trimmed and case-insensitive. Missing/invalid configuration denies new logins. Password verification runs even for an incorrect email, failures share one response, and every attempt consumes the existing shared limits. The login no longer prefills the account address, and the recovery note no longer refers to the unsupported `ADMIN_PASSWORD` variable. Tests cover rejected email/password combinations, direct malformed input, missing configuration, normalization, password verification for a wrong email, shared throttling and successful session creation. The security suite now has 35 passing tests. Production deployment of this follow-up requires `ADMIN_EMAIL` in the correct Vercel project; it does not resolve the separately reported live configuration/storage failure or introduce email verification/MFA.
- Existing cookies and hardcoded/default passwords no longer work. Administrator bootstrap is deliberate and fails closed; public unauthenticated password reset is prohibited.
- Passwords changed through the admin modal must have 12-256 characters. Scrypt uses explicit strong parameters; function memory must support the documented in-flight cost.
- Public HTML is dynamic because script nonces must be fresh. Images/media retain their separate caching policies. Browser appearance and interactions were preserved, but latency and hosting usage should be checked in the intended environment.
- Uploads are limited to 4 MiB through Vercel Functions. The previous larger slot constants could not pass normal Vercel ingress. Larger direct uploads require a separately designed private quarantine/finalization flow.
- Existing JSON, content, media and credentials were not automatically deleted, imported, overwritten or rewritten. Enquiry capacity now rejects new storage instead of silently dropping old records.
- The ESLint adapter is limited to the API actually used by the current Next plugin. Its compatibility is regression-tested; revisit it when upstream patches/removes the vulnerable dependency chain.
